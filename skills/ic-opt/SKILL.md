# IC-Opt operator

You run Spectre/OCEAN optimizations with `ic-opt` and explain the results.
The user owns the design question; you own the mechanics and the evidence.

## Mental model

- `spec.yaml` = WHAT: testbenches, corners, variables (grid), metrics, constraints, objective, simulator limits, budget. A metric is an OCEAN expression, an EM device's `quantity`, or `saturation_margin: {instances: [M1, M2]}` with `unit: V` and its `testbench` -- the smallest `|vds| - |vdsat|` of those transistors, computed from that testbench's operating points (a DC-only testbench as a cheap first gate, constrained `ge 0.05 V`: `skills/author-spec/SKILL.md`).
- Recipe = HOW: `main(run, **params)` composing blocks. Built-ins: `optimize`, `fix_run`, `coarse_to_fine`, `signoff`, and for the device library `lib_design`, `lib_signoff`, `lib_tap`, `lib_refine`.
- Blocks: `env.doctor`, `netlist.import`, `points.{fixed,sobol,grid,one_at_a_time,from}`, `sim.evaluate`, `opt.suggest`, `opt.optimize`, `opt.advise`, `opt.revoke_advice`, `analyze.best`, `analyze.report`; device library `lib.{load,coverage,query,suggest,region,densify,index,pick}`; process profiles `em.validate_profile`. `ic-opt blocks` lists them, `ic-opt describe NAME` shows a signature.
- Results: `PROJECT/.icopt/observations.jsonl` (fact table), `advice.jsonl` (advice given, only when some was), `steps.jsonl`, `sims/<obs>/<tb>/<corner>/`, `reports/report.md|html`.
- Re-running continues: `opt.optimize` stops when its step holds `budget` observations; raise `budget` to go on.

## Procedure

1. **Spec.** New project: write `spec.yaml` from the user's testbenches (Maestro export roots must contain `netlist/input.scs`), variables with bounds and step, OCEAN metric expressions, constraints, objective -- the procedure, every section's rules and four complete examples (circuit, EM device in a circuit, circuit and device together, device only): `skills/author-spec/SKILL.md`. Old project (`opt_requirement.md`): `ic-opt migrate OLD NEW`, then read `NEW/MIGRATION.md` for the matching command (it lists resource values filled with 0.1 defaults: confirm them with the user). A project or library part whose store an earlier ic-opt wrote: `ic-opt migrate-store PROJECT --dry-run`, then the same without `--dry-run`, once, before its next run and before any spec edit — until then its EM observations are not reused, its Spectre ones only while the spec stays unchanged, and those the 0.2.0 release wrote not at all. A resource the old spec left to its default gets that default written in first (0.2.0: `simulator.threads_per_run: 10`), then the store is restamped, then the user's own value goes in (README, "Stores written by an earlier version"). Ask before inventing bounds, metric formulas or constraints — and never invent resources: `simulator.parallel_jobs` / `threads_per_run` / `timeout_s` and `em.threads` / `memory_gb` / `timeout_s` are required and come from the user. `simulator.license_queue_timeout_s` (Spectre's `+lqtimeout`) is optional: leave it out unless the user gives a value, and Spectre waits for a license as it does by itself. A spec `ic-opt migrate` converted from a 0.1 project carries 0.1's `license_queue_timeout_s: 900` (0.1 always passed `+lqtimeout 900`; MIGRATION.md lists it): keep it, or remove it if the user wants Spectre's own wait.
2. **Environment.** `ic-opt doctor PROJECT [--ssh-profile P] [--cshrc F]` — tools, license, exports, site envelope, budget must all be `[ok]` (`[WARN] machine` is advisory: the entry exceeds what the host reports). Install the `report` extra (shap, lightgbm) before a run whose report must say which variables matter: without it the SHAP section reads `_not available_`. `uv venv` carries no pip: `uv pip list` is the environment snapshot, `python -m pip` fails there without meaning anything. It asks only for the tools the spec's pipeline runs: `spectre` / `ocean` / the license for testbenches, the EMX binary (`em.binary`) for devices; a pure EM spec needs no Spectre. `~/.ic-opt/site.yaml` has one entry per host — `local` (the machine running ic-opt) and one per `--ssh-profile` name — each with `max_threads` and `max_memory_gb`: required, no defaults, and a missing file, entry or field refuses with the entry to add. The numbers are the user's; never write them yourself. The simulation host's entry bounds the jobs; `hosts.local` is also the budget of the device library's own compute (model fits, BLAS threads, prediction chunks), which always runs on the machine running ic-opt, so library work needs it even when every simulation is remote. Cadence env file lives on the simulation host and is given explicitly: `--cshrc`, `IC_OPT_CADENCE_CSHRC` or `cshrc:` in that host's entry; a `.csh` / `.cshrc` / `.tcsh` / `.tcshrc` file is sourced by csh, any other by sh.
3. **Plan.** `ic-opt run RECIPE PROJECT [params] --plan`. Read every line: the doctor checks (`[ok]` each; `[WARN] machine` is advisory), one `[plan] netlist.import <tb>` per testbench (a `FAIL` names a variable the export lacks or a corner with no include line; a `WARNING` names a parameter a corner sets that the export never uses -- set it through the corner's `options` instead), the `opt.optimize` line (simulations per point -- a ceiling with EM devices, `EMX results cached per geometry`; with devices from a library table `(... + N device measurements of library rows, no simulation)` and `no EMX runs (the devices are library rows)` -- batches, `jobs × (threads_per_run + 1) threads` on which host, the spec budget; the `+ 1` is the OCEAN process that extracts a testbench's metrics beside Spectre, an EMX job counts `em.threads`, and the run's first line gives the same figure with `peak_threads` and, apart from the peak, the strategy's threads between batches), with no strategy named the `strategy auto: <name> (<why>)` line (which strategy the run uses and why), the `opt.optimize ... current design (the exported netlists) first: ...` line (the design as exported, evaluated first; `no current design: ...` says why there is none -- testbenches that disagree, a value outside a variable's range, a spec with EM devices -- and a value between grid points is `moved to` the nearest one) and, for `openbox_*`, `initial design N points (S start points first): the surrogate proposes K of M` (the first N observations are the start points then a Sobol design, whatever the batch; K counts every later point, from the batch that reaches the end of the design on, once the history at a batch's start holds one more successful point than there are variables; K = 0 warns: raise the budget, use a smaller batch or a smaller `initial_trials`); for `metric_gp` the line reads `metric_gp initial design N points: the model proposes K of M` (its model needs one successful point before a batch starts). A spec whose devices come from a library table prints one doctor line per device, `library:<device>: <stratum> at <f> GHz: <n> rows on the grid in <m> of <total> combinations, prefer <rule>` (the table on the variables' grid: `n` rows occupy `m` of the grid's combinations, and only those `m` are candidates), in place of `device:<id>` and the EMX checks, and `[note] em: not used` when the spec keeps an `em` section. A `WARNING` inside the license line comes from the SSH client's banner, not from ic-opt. Show the user the sequence, the simulation count and the resources; this is the approval point — get a yes before dropping `--plan`.
4. **Run.** Same command without `--plan`. Long runs: run in the background and read `steps.jsonl` / `observations.jsonl` for progress, and the per-batch lines `[evaluate] ... metric X failed on N of M points` / `constraints violated -- ...` (written line by line, so a log the run is redirected to shows them batch by batch): a metric failing on part of the space is a reason to stop and fix the expression, not to let the run go on. When a point needs 20 or more simulations (testbenches × corners), its simulations run in an order learned from the project's observations and the point stops at the first one that fails it (the plan says `up to N simulations per point`, each batch `K of N points stopped early, S simulations not run`); below 20 every simulation of a point runs unless `simulator.stop_at_first_failure: true` in the spec says otherwise, `false` runs every simulation whatever the count (a characterization run) -- measured: the stop won clearly at 62 simulations per point, was even at 18 and lost at 6 and 2, and `ic-opt run signoff PROJECT ... full=true` every corner of the points it re-checks. With EM devices or library devices bound into testbenches each device is measured first, and a point whose device fails a constraint (an SRF, a Q, an inductance window) or whose measurement fails runs no testbench simulation, whatever the count (the plan adds `the device measured first: ...`, each batch line `(D at the device)`); `stop_at_first_failure: false` runs every simulation there too. A `steps.jsonl` row carries `seconds` (the points' own durations added up) and `wall_seconds` (the clock time of the batch). A geometry that comes up again costs no EMX run, inside a batch too (the later point waits for the first one's result), so a run uses at most the planned simulations. Never exceed the host's entry in `~/.ic-opt/site.yaml` (a job bigger than the host is refused, also under `--plan`); `run.jobs` already trims `parallel_jobs` to fit. Nor the entry of the machine running ic-opt (`hosts.local`) with `simulator.strategy_threads` (default 1): the threads the strategy's own computation -- its models, torch for `turbo` -- uses while it proposes a batch, between batches, on that machine; raise it only to a number the user gives (an `OMP_NUM_THREADS` / `OPENBLAS_NUM_THREADS` / `MKL_NUM_THREADS` set lower still applies). EMX runs at once = min(`simulator.parallel_jobs`, host threads / `em.threads`, host memory / `em.memory_gb`), and `em.parallel_jobs` caps them below that (the plan line says `EMX at once ≤ N`) when the user allows fewer EMX than Spectre runs at once. To stop a run, one Ctrl-C: the last `steps.jsonl` row reads `interrupted`, the host's commands end with their process groups, and running the same command again continues (interrupted points are simulated again); check the host with a read-only `pgrep -u $USER spectre` before starting anything else there, and never start a second run in the same project meanwhile (the store's lock refuses it). On Windows an editable install cannot be reinstalled while `ic-opt.exe` runs: install every extra before the run.
5. **Read.** `ic-opt digest PROJECT [--step S] [--top N] [--json]` first: what is optimized, how far the run is, which constraints bind, where the good points are, where points gave no value and the issue texts they gave most often, the strategy's state (the `metric_gp` region's side: per variable the levels within side × weight / 2 of the centre in unit coordinates, weight 0.2 to 5), the advice given and how it fared (step 7) -- every number computed from the observations, written to `reports/digest.md` / `digest.json`; it takes no lock, so it reads a run that is still going. Version 3 adds: a stall line under Progress (batches since the best improved, `stalled` from three on, where the `metric_gp` region last restarted); a `verdict` column in the advice table (`helped` / `no_help` / `mixed`, with the run's best before and after the advice and the share of the period's points that came from it); a table of the variables by importance (mutual information with each metric the spec names, over the points that gave it; needs 20 such points); a line of what failed the points by stage (`render`, `spectre`, `ocean`, ..., `metric_failed`, `constraint_failed`, and how many were stopped early); and the advice `ic-opt advise` refused (`r1`, `r2`, ...: the history size and the reason; the file's content stays in `advice.jsonl` only). Issue texts are cut to 200 characters. Version 4 adds `library` (a section "Library devices" in `digest.md`) for a spec whose devices come from library tables: per device the table, the working frequency, the rule that ranks a combination's rows, the combinations on the grid (`m of total`, holding `n` rows) and how many the run visited, and for the best feasible points the row each device took -- `part/obs_id`, its geometry, its electrical values (the device's variables and the ranking column) and its footprint; read which rows the good points share before advising a range of electrical values. The report's Best observed names the best point's row the same way. Then `reports/report.md`: Summary (feasible count, best point, binding constraints, worst corner), Best observed, Top feasible candidates, Constraint margins (judged on every corner under `all_corners`), Parameter importance (SHAP; a device's quantity is ranked among that device's variables only, `(its device's variables)`), Corners (per-corner best as a table, failures per corner -- a point counts at every corner it fails at -- and violations per constraint and corner), Where the best points are (per variable the span of the 5 best feasible points one level wider, and whether they lie at the spec's bound); values print with their unit (32 GHz, 13.93 dB) and `report.html` puts each figure under its section; figures `feasible_convergence`, `constraint_margins`, `bottleneck_weighted_score`, `convergence`. Cross-check with `observations.jsonl`: one JSON object per line with `obs_id`, `params` (variable -> text value), `origin` (`start`, `suggest:<strategy>:<tag>` -- `init` / `acq` for `openbox_*`, `init` / `grid:<k>` / `tr:<r>:<k>` / `wide:<r>:<k>` / `anchor:<r>:<k>` for `metric_gp`, with `@<id>` appended when chosen inside advice `<id>` --, `advice:<id>` for an advice's start row, `user`, ...), `children` (a dict keyed `<testbench>/<corner>` or `<device>/nominal`, each with `unit`, `corner`, `status`, `metrics`, `issues`, `sim_dir`, `seconds`, for a library device's child `library_row` -- the row the point took: `stratum`, `part`, `obs_id`, `geometry`, `values` (its electrical values at the working frequency), `footprint`; no path -- and, for a Spectre child whose results held them, `operating_points`: `{instance: {quantity: value}}` for the transistors, quantities `region ids vgs vds vbs vth vdsat gm gds gmoverid cgs cgd` where the simulator gave a number -- absent on older rows, EM devices and `simulator.operating_points: false`; for reading, no strategy uses them), `metrics` (the selected corner's), `fom`, `objective` (minimization form), `feasible`, `constraint_penalty`, `status`, `issues`, `simulations`, `cache`, `step`, `spec_fingerprint`, `pipeline_fingerprint`; read one line before writing a script against it. A point with fewer children than testbenches × corners was stopped at its first failure: `not_run` lists the children it did not run (the field is absent on every other point; read it, not the line), its `issues` hold `not simulated: <n> of <m> children (stopped after <testbench>/<corner>)`, its status is that child's (`constraint_failed`, `metric_failed`, `failed:<stage>`), it is never feasible, and the digest counts such points (`stopped_early`, `simulations_not_run`). The digest's `stopped_at` says where they stopped: per `<testbench>/<corner>` how many points stopped after it, most first (`digest.md` prints the three largest under the counts). A point stopped at its device holds only its device children (`<device>/nominal`), lists every testbench child in `not_run` and keeps the device's metrics in `metrics`; the digest's `stopped_at_device` counts such points. A `saturation_margin` metric appears in `metrics`, the digest and the report like any other metric (a value in V); when the operating-point table lacks a transistor it names, the point is `metric_failed` and the child's issue names the transistor: `metric SAT_MARGIN failed: no operating point for M7`.
6. **Advise.** Tie every recommendation to observations: which constraint binds (margins), which variables matter (importance), whether the search saturated (convergence), which corner fails (corners). Suggest the next recipe or spec change, not a vague "run more". A `signoff` whose re-check found no point feasible at every corner, while its search corner passed, is a reason to run another round: `ic-opt run signoff PROJECT <same parameters> rounds=<N>` (plan first) tightens each constraint the best re-checked point missed by the miss and searches again; a re-run keeps each round's search points, so raising `rounds` adds rounds. Read the misses in `.icopt/reports/signoff_rounds.json` (per round: the limit searched under, the worst value and its corner, the miss, the next limit, and why the rounds ended). Rounds that ended `nothing_to_tighten` (the best point failed a simulation or lost a metric), `limits_cross` (a metric bounded on both sides spreads across the corners more than its window) or `rounds_used` with misses that do not shrink are a design or spec question for the user, not a reason for more rounds.
7. **Give the run advice** (optional; ic-opt calls no language model -- you, or the user, are the one who reads and advises). After a run has stopped: read what it found (`ic-opt digest PROJECT`), write an advice file, adopt it, continue the run with a larger budget:
   ```yaml
   # advice.yaml -- values in the spec's own text form, on its grid
   author: "agent: <model>"                 # required
   reason: "the 5 best points all have W1 >= 2u; L2 changes nothing"   # required: recorded with the advice
   start: [{W1: 2.4u, L2: 0.1u, IB: 40u}]   # complete rows to evaluate first (every strategy)
   ranges: {W1: [2u, 4u]}                   # narrower ranges, inside the spec's (metric_gp)
   fixed: {L2: 0.1u}                        # hold a variable at one level (metric_gp)
   vary: [W1, IB]                           # only these move, the others stay at the search region's centre (metric_gp)
   ```
   `ic-opt advise PROJECT advice.yaml` prints what it adopted (`[advise] adopted a2 (since 40; in effect from the next batch): ...`, one line per value it moved onto the grid) or refuses with what to change; then `ic-opt run <same recipe> PROJECT budget=<done + more>` (plan first). A run you mean to advise between batches from its start: give every call the budget it is meant to reach, `ic-opt run optimize PROJECT budget=<k x batch> total=<N> ...` for k = 1, 2, ...; the step's first call sizes the initial design for `total` and records it (`.icopt/steps.json`, the plan line says `initial design n points (sized for a budget of N)`), so the run proposes what one call with `budget=<N>` proposes (without `total` the first call's own budget sizes the design, and every later call keeps that size). `ic-opt advise PROJECT --list` shows every advice and which is in effect; `--revoke a2 --reason "..."` ends one; a new advice ends the one before (one at a time). A store holding the problem at several sets of corners (the `signoff` recipe) needs `--corners tt`. While a run goes the command is refused (the run holds the project).
   What an advice may do: add start points; narrow where `metric_gp` looks with four fifths of each batch after its initial design (points `...@a2` in `origin`, start points `advice:a2`). What it may not: widen or move the spec's ranges (a range outside them is refused -- the spec is the user's; propose a spec change to the user instead), change constraints, the objective or the budget, move the initial design, or take the free fifth of each batch, which chooses as the run would without advice so that wrong advice does not end the search. `openbox_gp_eic` and `turbo` take the start rows only (a run line says which parts are unused). What advice did, measured on 8 test problems and 12 test circuits (runs of 200 points, advice at 40): right ranges ended better than without advice on 2 problems and 4 circuits, worse on none; wrong ranges ended worse on 1 problem and 1 circuit, and 139 of 140 runs kept their share (ended at least as well as the run without advice at 40 points plus a fifth of the rest). On 8 further circuits, looked at once afterwards: right ranges ended better on 30 of 40 runs; wrong ranges, never revoked, ended worse on 3 of the 8 circuits, and 35 of 40 runs kept their share -- most, not all. The digest's suggested ranges say where the best points found lie; taken as they are as an advice they helped nowhere (on the circuits 39 runs ended worse, 20 better) -- advise from a reason beyond them, and revoke an advice whose `@<id>` points do no better than the others. The digest's advice table gives per advice its period (from the history size it was adopted at to the one the row that ended it was written at), and for the points under it and the others proposed in that period alike: points, feasible, no value, best objective -- compare the two sides of one period, not points proposed after the advice ended; its start points with their status, objective (only when feasible) and `(best so far)` when one became the run's best; and a line under the table when the run's best point lies at a bound of the advice's range that is not the spec's (better points may lie beyond it: a wider advice, never wider than the spec, looks there).

   Tools on your side (optional; you compute them, outside ic-opt): before advising you may turn what you know of the circuit into numbers. A gm/ID lookup table of the process -- from a single-transistor DC sweep you run on your own, per device type and channel length, not an ic-opt run -- turns a target gm/ID and a branch current into a width (W = I_D divided by the table's I_D/W at that gm/ID and length; roughly 4 to 10 S/A is strong inversion, 10 to 18 moderate, 18 to 25 weak, depending on the process), so that a start row names a design you reasoned about. A constraint implies ranges: a power budget bounds the branch currents from above (their sum is at most the budget divided by the supply); a slew-rate constraint bounds a branch current from below (at least the slew rate times the load capacitance); a saturation margin (V_DSAT plus about 50 mV at most the V_DS the branch leaves) bounds V_DSAT from above and so gm/ID from below; a gm/ID range and a current range then give a width range, from the smallest current at the smallest gm/ID and length to the largest at the largest. These are inputs to `ranges` and `start` advice, never to the spec: its ranges, constraints and objective stay the user's. The rules come from two papers, MultiForm (TCAS-I 2025, its search-bound refinement) and OTA-LUT (DATE 2025, its lookup-table sizing). Neither was measured here: no ic-opt run has tested them.

   How to advise -- from eight recorded sessions (an agent read the digest and the netlist every 40 points and advised with these commands, on four test circuits; seven ended better than the run of the same seed without advice, one worse) and the scripted measurements above:
   - **Leave the run alone when the evidence is thin**: fewer than three feasible points, or a run that still improves with every batch. The sessions that did so in their first rounds lost nothing by it.
   - **Evidence that held up**: a split of "where points gave no value" that names the same variable and the same side in consecutive digests; the constraint that binds, with a reason from the circuit for which variable moves it. **Evidence that did not**: the suggested ranges taken as they are; a rank correlation of one digest (they changed sign from one digest to the next as the search moved).
   - **Prefer start rows to ranges** when the claim is about one design ("this point with more bias current"): a start row costs one simulation and narrows nothing. Check what it will cost in the constrained metrics first (a row that tripled the bias current went over the power limit).
   - **Review at every round, before anything else**: the advice table's two sides for the advice's period. Revoke an advice whose points do no better; measured, a review every 40 points took most of the loss out of wrong advice and cost right advice next to nothing. Know what the comparison cannot show: the free fifth chooses in the same search region, which the advised points have moved, so an advice can look no worse than the others and still hold the search away from a better region. In the one session that ended worse the agent kept an upper limit read off the first random points; the run's best point came from the free fifth, beyond that limit.
   - **A limit read off the initial design is weak**: in random points many variables differ at once. Give it as a range you will widen, and widen it (a new advice) when the best points press against its bound -- the digest says so under the advice table.
   - **Say in `reason` what the advice rests on and what would show it wrong**; the next review reads against that.

## Recipe cheatsheet

```bash
ic-opt run optimize PROJECT budget=60 [total=N] batch=10 [strategy=auto|metric_gp|openbox_gp_eic|turbo|random] seed=0 [corners='["tt"]'] [initial_trials=N] [current=false] [start=start.json]
# strategy=auto (the default of optimize, signoff, coarse_to_fine): metric_gp for a spec without EM devices, at any
# corners, and for one whose devices come from library tables ("library devices: no EMX in the loop"),
# openbox_gp_eic otherwise; the line "strategy auto: <name> (<why>)" says which
# the design as exported is evaluated first (current=false: not), then the rows of start.json (a JSON list of parameter rows,
# the format of fix_run's points file); origin `start`; never twice, also when the run continues
# openbox_*: the first initial_trials observations (default min(2 x variables, budget // 2)) are the start points then a Sobol
# design; the surrogate proposes everything after them, the rest of a straddling batch included -- `--plan` prints "the
# surrogate proposes K of the N new points" and warns when K is 0; origins end in :init / :acq; a variable whose range is
# positive and spans a decade (upper / lower >= 10) is searched on a log scale, its design even per decade (as metric_gp's)
# turbo: a Latin hypercube design of 2 x variables (start points count), then the trust region; origins end in
# :init:<r>:<k> / :tr:<r>:<k>; the same log scale as openbox_*. A run with such a variable started by an earlier
# version and continued now proposes differently from the one that started it (same history, other scale); without: as before
# metric_gp: one model per metric, the spec's formulas on their samples, no penalty; design initial_trials (default
# min(max(2 x variables, 8), 20, budget // 2)); origins end in :init / :grid:<k> / :tr:<r>:<k> / :wide:<r>:<k> / :anchor:<r>:<k>;
# named explicitly it refuses only EM devices EMX simulates in the loop; at several corners its models see each metric at
# its worst over a point's corners
# every strategy proposes with simulator.strategy_threads threads (default 1: BLAS / OpenMP, and torch for turbo)
ic-opt run fix_run  PROJECT points=points.json [waveforms=waveforms.json] [corners='["tt","ss"]']
ic-opt run coarse_to_fine PROJECT coarse_budget=40 fine_budget=40 [strategy=auto] [current=false] [start=start.json]   # current/start for the coarse step
# auto: metric_gp in both steps, or (EM devices) openbox_gp_eic then turbo; a named strategy runs both steps
ic-opt run signoff  PROJECT corner=tt budget=60 top=5 [strategy=auto] [current=false] [start=start.json] [full=true] [rounds=1] [tighten=1.0]   # current/start for the search step
# rounds=N: while the re-check finds no point feasible at every corner, each constraint its best point misses is tightened
# by tighten x the miss (an upper limit down, a lower one up, from the limit that round searched under) and the search at
# `corner` runs again -- step search@tt#2, budget more points, handed the earlier searches' points, on a copy of the spec --
# its top points re-checked under the constraints as written (signoff#2); at most N searches. One line per tightened
# constraint (limit, miss, next limit); .icopt/reports/signoff_rounds.json holds every round and why they ended. The later
# searches are other problems (their own fingerprint): the digest shows the first search and every re-check. With rounds
# above 1 a limit written with an SI prefix (50m V) is refused
ic-opt run lib_refine PROJECT [device=ID] [steps=1] [n=8] [prefer=max:Qmin] [threads=N memory_gb=G] --plan   # after a run whose devices come from library tables: real EMX on the n geometries next to the best point's row the table lacks (predicted inside the run's window, ranked by prefer, preflighted), adopted into the row's part; the last line is the command that continues the run (docs/em/library.md 7c)
ic-opt run my_recipe.py PROJECT key=value          # custom composition
ic-opt call analyze.best PROJECT k=5               # any block, spec/store/observations filled in
ic-opt advise PROJECT advice.yaml [--corners tt]   # advice for the next batches (step 7); --list; --revoke ID --reason TEXT
```

Custom recipe skeleton:

```python
from ic_opt import blocks as b
def main(run, *, n=12):
    deck = b.import_netlists(run.spec, run.executor, run.store)
    obs = b.evaluate(run.spec, b.points_sobol(run.spec, n), run.executor, run.store, deck=deck,
                     step="screen", cshrc=run.cshrc, parallel_jobs=run.jobs, limits=run.limits)
    run.note(f"report: {b.report(run.spec, obs, run.store)}")
```

Point-level status: `ok`, `constraint_failed`, `metric_failed` (a metric's OCEAN expression returned nil / a non-scalar / nothing, or a requested waveform nil: the child keeps the metrics that did extract and the point keeps the nominal corner's, so a wrong expression costs that metric, not the point), `failed:<stage>` (render / spectre / ocean / pcell / emx / pick / bind_nport / measure) — the child's `issues` and `sim_dir` (`spectre.stderr`, `metrics/ocean.log`) say why.

## Reading failures

- `doctor` `[FAIL] tools/license/emx` → wrong or missing cshrc; `export:<tb>` → Maestro export not at `maestro_point_root/netlist/input.scs` on that host. `operating points:<tb>` is information: `in the export (<name>)`, `added by ic-opt (statement)` (an info statement after the export's DC analysis), `added by ic-opt (DC analysis and statement)` (a DC analysis appended after every other analysis), or `off`; a child without them (`operating_points` absent) is not a failure, unless a `saturation_margin` metric of that testbench reads them (step 5).
- `netlist.import` `ValueError: <var> was not found` → the variable is not a top-level `parameters` entry in the exported netlist (only those may be swept), and every circuit variable must be one in **every** testbench's netlist (a device's variables are consumed by `devices` and are not); `--plan` fetches the exports and prints `[plan] netlist.import <tb>: FAIL ...` for one that lacks a variable, so read the plan before the run. `[plan] netlist.import <tb>: WARNING the corners set [...] which this export declares ... but never uses` → the export writes that quantity as a literal (ADE exports put the simulation temperature in `simulatorOptions ... temp=27`): the corner value changes nothing; set it through the corner's `options` (`options: {temp: "125"}` rewrites the `simulatorOptions` statement), never edit the export.
- `failed:spectre` with a license message → retry later; `failed:ocean` → OCEAN itself produced no scalars (check `metrics/probe.ocn`); `metric_failed` → one expression returned nil (`no_value:nil` in `ocean_scalars.tsv`: the call found nothing on this point, e.g. `compressionVRI(...)` on a gain that never falls 1 dB inside the swept power -- it depends on the design point, so it comes and goes), a non-scalar (`non_scalar:<SKILL type>`, e.g. a waveform from `bandwidth(...)`: every point fails) or a non-finite value, or a `saturation_margin` metric found no operating point for a transistor it names (`no operating point for M7`: a name the table does not hold -- copy it from the digest's operating-point table -- or results without operating points); `skills/author-spec/SKILL.md` lists the replacements that yield a number on every point; the other metrics are in the observation. It is not a skipped point: it has no objective, so the strategies take it as failed -- OpenBox as a failed trial (its models see the worst value observed there), `turbo` as the worst target of the history, `metric_gp` as a point that gave no value (each metric's model still uses the metrics it did give) -- which steers the search away from wherever the expression fails (`failure_penalty` is ignored since T17.0b) -- `sim.evaluate` prints `metric X failed on N of M points` per batch; when it does, stop, fix the expression, and continue (a fixed point is re-simulated when it comes up again).
- `[FAIL] library:<device>` → the device's library table cannot be resolved on the machine running ic-opt: no `library.yaml` at `library.root`, an unknown stratum (the message lists them), a variable mapped to a column the index lacks (listed), ports that are not the table's, or no row on the variables' grid (the message gives each column's range in the index beside the variable's: move the range or the frequency). `failed:pick` → the point's combination holds no row of the table (a point from elsewhere -- a `fix_run` row, another project's -- or a library changed since): the issue names the values and the nearest combination the table holds.
- `failed:<stage>` with `timed out after Ns` → that point's command ran past `simulator.timeout_s` / `em.timeout_s` and was killed with its process group; the other points ran on. Ask the user before raising the timeout: a hung point can also be a pathological design point.
- Stopped by Ctrl-C → the last `steps.jsonl` row has status `interrupted` with `recorded` / `interrupted` / `not_started` point ids; interrupted points were not recorded, and running the recipe again simulates them (nothing queued had started).
- `BudgetExceeded` → raise `budget.max_simulations` in `spec.yaml`: the problem fingerprint leaves the budget out, so the observations keep being reused and counted. The budget counts every simulation the store holds, also the observations an edited spec (metrics, variables, ...) no longer reuses: after such an edit raise it or start a new project. That holds for a store an earlier ic-opt wrote only after `ic-opt migrate-store PROJECT`: its old stamps match the spec only as it was, and raising the budget first cuts the run off from them.

## EM devices

A spec with `devices` (pcell generator instances: `generator`, `profile`, `ports`, `fixed`, `variables`), `em` (EMX settings, `process_file` on the simulation host) and `bindings` (which testbench nport instance takes which device's sNp, `terminals` in sNp column order; a `null` terminal drops that instance terminal — a tap wired twice, a grounded one — and `bind_nport` rewrites the instance to the kept ones) runs the EM circuit pipeline `pcell → emx → bind_nport → spectre → ocean → extract` with the same recipes; a spec with devices but no testbenches runs `pcell → emx → measure` (device metrics: `quantity` Lp/Qp/Ls/Qs/k at `frequency_hz`, or Lp_lf / Lp_res / Qp_peak / SRF_p / k_lf). Set `IC_OPT_PROFILE_DIRS` to the directory holding the private `<profile>/rule.yaml`. Real EMX runs need the user's approval after `--plan` (keep `simultaneous_frequencies: 0`; jobs × `threads` and jobs × `memory_gb` fit the host's site.yaml entry); EMX results are cached per device by GDS + ports + physics settings + the process file's content (never its path). `ic-opt migrate` converts em-opt's `em_opt_requirement.md`. Failures: `failed:pcell` (unbuildable geometry / DRC), `failed:emx:<device>`, `failed:bind_nport` (instance or terminal count), `failed:measure` (quantity outside the sweep, no resonance for SRF). A device's `topology` (`drives` as `[plus, minus]` pairs, `grounded`) defaults from its ports: four ports drive the secondary reversed, `[[P1, N1], [N2, P2]]`, the built-in families' winding sense; an `ok` point whose `issues` report `k_lf = … < 0` comes from a generator that winds its secondary the other way — the issue names the `topology:` line to state in the spec (docs/em/devices.md).

A device may instead come from a library table (`devices[*].library: {root, stratum, frequency_hz, srf_margin?, prefer?}`, `variables` mapping index columns such as `Lp`, `Ls`, `k` to spec variables of electrical values; every device of the spec, or none): its candidates are the table's rows. The pipeline is `pick → bind_nport → spectre → ocean → extract` plus `measure` for the device -- `pick` takes the row of the point's combination (the best by `prefer` when it holds several) and binds that row's real sNp, reordered to the binding's terminals when needed -- so no EMX runs, no `em` section is needed, the budget counts the testbench simulations only, `strategy=auto` runs `metric_gp`, and the device's child runs first: a point that fails its SRF or Q constraint runs no simulation unless `simulator.stop_at_first_failure: false`. The strategies propose only the combinations a row sits on. The library is read once per run; a library that grew is a new pipeline generation (the combinations already evaluated keep their observations). Guide: `docs/em/library.md`, "Library devices in a circuit spec".

## Device library and process profiles

A library is a directory of em_only run stores plus `library.yaml` (strata = family × metal body, parts, dims, quantities named after the measure kernel); `ic-opt call lib.<name> LIBRARY_ROOT key=value` answers from it (dicts print as JSON). Its datasets, calibrations and fitted models are cached in `LIBRARY_ROOT/.cache/`, or in `cache_dir=DIR` (every `lib.*` block, `lib_design`, `lib_signoff`); a library the user cannot write to still answers — the cache then goes to `~/.cache/ic-opt/<key>/`, the answer's `notes` say so, and the files already in its `.cache/` are still used. `lib.load` / `lib.coverage` show what is there (`coverage` also each part's device: generator, profile, the metals its windings sit on -- a stratum named after one metal body may put the primary on it or under it -- and the stratum's `note`, and `cached`: per quantity `model` / `calibration` / `none`, what a query will have to fit first); `lib.query stratum=S 'params={...}'` returns per quantity `measured`, `predicted` (mu with calibrated ~95% bounds `lo`/`hi`), `uncertain` (sigma / mu above the quantity's ceiling `rel_sigma_max`: the call's `rel_sigma_max=`, else the quantity's in `library.yaml`, else 0.15), `out_of_domain` (criterion + reason + nearest rows) or `above_sweep` (SRF); a curve the manifest builds from other columns (`model: ratio` or `model: resonance` in library.yaml) adds `composition` — its base value (the low-frequency value for `Lp` / `Ls` / `k`, the peak `Qp_peak` / `Qs_peak` for `Qp` / `Qs`), the `ratio` or the `SRF`, `resonance_factor` and `residual`, whose product is the value; `lib.suggest stratum=S 'targets={"Lp_lf": {"target": 1.2e-9, "tol": 0.03}}' objective=max:Qp_peak` lists measured designs first, then predicted candidates that meet the targets with their whole interval and pass the real generator + DRC audit. A declared curve (`Lp`, `Qp`, `Ls`, `Qs`, `k`) answers at any frequency inside the parts' sweeps, not only at its `anchors_ghz`: name it `<curve>@<GHz>` (`Lp@<f>`) in `quantities`, targets, objective or trend and the library measures that column again from every row's sNp once (cached), then answers and models it like a declared one; a curve the stratum does not declare, or a frequency outside every part's sweep, is refused with what exists (`lib.coverage`'s `any_frequency` line names both). Answers carry `footprint` (`width_um`, `height_um`, `area_um2`: the box around the drawn device without its EMX ground fixture) — a library row's from its GDS, a candidate's when `verify_build` drew it, `lib.query` elsewhere only with `footprint=true` (draws it, no EMX); a null one comes with `footprint_why`. To see the rows themselves by electrical value at one working frequency, `lib.index stratum=S frequency_ghz=F ['grid={"Lp": [LOWER, UPPER, STEP], ...}'] [prefer=max:Qmin] [srf_margin=M] [out=FILE]` summarizes the rows that have every curve there (kept, dropped and why, column ranges, sweeps) and with a grid the cells they fill (nearest level per coordinate, logarithmic where the range spans a decade, rows in a cell ranked by `prefer`); `lib.pick stratum=S frequency_ghz=F 'targets={"Lp": V, ...}' 'grid={...}' [n=N]` returns the nearest occupied cell's best rows — measured values, geometry, footprint, part / obs id and the sNp path — with `exact` and the `distance` in levels; the grid (the user's numbers) says what counts as the same value. For sweep ranges use `lib.region stratum=S 'targets={"<quantity>@<f>": {"min": <a>, "max": <b>}, ...}' group_by=DIM,DIM trend=QUANTITY:DIM` — example: an inductance window and a minimum Q at one frequency; `<f>` is any frequency inside the parts' sweeps, the numbers (SI units) are the user's, and a `{min, max}` window works in `lib.suggest` too. It grids the region meeting every target (bracketed by a coarse pass with the windows `relax` wider, 0.10 unless given: raise it when the region looks cut short) and returns per-dim ranges at two levels, `robust` (whole calibrated `k`-sigma interval inside, where a sweep should centre; the answer echoes `k` and each quantity's `rel_sigma_max`) and `mean` (prediction inside, the optimistic envelope), plus `binding`, `edge`, `group_by` rows, `trend`, candidates and the measured rows that meet all; per-dim ranges are projections, so quote the `group_by` rows. To grow a library where its models are least sure, whatever the targets, `lib.densify stratum=S n=N [quantities=Q,Q] ['bounds={"DIM": V, "DIM": {"min": A, "max": B}}'] [score=ceiling|typical] out=FILE` proposes N geometries by model uncertainty inside the bounds (each scored by its raw posterior sigma over the quantity's confidence ceiling `rel_sigma_max`, or with `score=typical` over the quantity's held-out median error; picked greedily with the other candidates' variances updated as if each pick were measured) and reports the pool's sigma `before` / `after`; FILE is the `candidates=` of `lib_signoff ... top=N adopt=true --plan`, which is the approval point. `ic-opt run lib_design PROJECT library=ROOT` optimizes an em_only spec on predictions (no EMX, no budget spent); `ic-opt run lib_signoff PROJECT library=ROOT candidates=REPORT --plan` then real EMX compares predictions with measurements (z, inside) and `adopt=true` folds the rows back into the library. A circuit that binds a tapped transformer needs tapped S-parameters (taps cost Q, a few per cent for a same-metal tap; L and k move little, so geometries are found on the untapped tables): `ic-opt run lib_tap PROJECT library=ROOT stratum=S 'taps={"primary": "same", "secondary": "same", "measure": "grounded"}' 'window={"frequency_ghz": F, "ranges": {"<index column>": [LOWER, UPPER]}}' --plan` (or `rows=FILE`: a `lib.index out=` table, a `lib.pick` answer, a list of part / obs id) builds each row's tapped twin (an xfm_bs or xfm_ms table; an xfm_ms secondary, the multi-turn winding, takes only a via-stack tap at least two levels below it, never `"same"`) -- the row's own geometry and fixture, the taps added, nothing else -- preflights every twin through the generator and the DRC gate without EMX (the plan lists refusals and the rows' own EMX peak memory, for `memory_gb=`), then runs real EMX and reports twin / row ratios; `adopt=NEW` adds the twins as a new stratum (library.yaml backed up first). Never present a `predicted` value as measured; say which answers were out of domain and why. Model fits run in spawned worker processes: Python you write that fits library models (`Library.models`, `lib.region`, `lib.suggest`, `lib.densify`, the library recipes) must be a script file with its top-level work under `if __name__ == "__main__":` — code piped to `python -` on standard input breaks the workers; `ic-opt call` / `ic-opt run` need nothing. Guide: `docs/em/library.md`.

A new process needs `<profile>/rule.yaml` (authoring guide `skills/author-process-rule/SKILL.md`) proven by `ic-opt call em.validate_profile PROFILE_DIR proc=SITE.proc generate=true` (exit 1 on any failed stage) before any EMX run. When the `.proc` lives on the simulation host, add `--ssh-profile P`: `proc=` is then that host's path, read through SSH into a temporary directory and deleted after the check.

## Windows controllers

README "Platforms" lists what a Windows controller needs and the traps found in acceptance: the OpenSSH client and `tar`, Git Bash rewriting `--cshrc /home/...` unless `MSYS_NO_PATHCONV=1` (or `cshrc:` in site.yaml), torch below 2.9, UTF-8 output regardless of the code page, export trees handled through extended-length paths. The repository's tests need the symlink privilege (they skip without it). An editable install is locked while a run goes.

## Remote hosts

`--ssh-profile P` (an OpenSSH alias or `user@host`) runs every simulation on that host, within its `P` entry of `~/.ic-opt/site.yaml`; the spec's paths are remote paths, netlists are fetched through SSH, results come back to `.icopt/`. Nothing on the controller reads remote paths directly (see `docs/adr/0001-remote-filesystem-boundary.md`). A command that times out is ended with its whole process group, on the host too (it runs under `setsid`; the timeout's message says how the cleanup went), so no stray Spectre / EMX keeps the host's cores.

## 0.1 command line

`ic-opt PROJECT --real|--doctor|--continue N` (0.1) is refused since 0.3 (exit 2; nothing is migrated or run). Convert once with `ic-opt migrate PROJECT NEW` (skip it when PROJECT already has `spec.yaml`: 0.2 converted it in place, so NEW is PROJECT), then take the command `NEW/MIGRATION.md` names through Procedure steps 2–4. `--doctor` → `ic-opt doctor NEW`, `--continue N` → the same `ic-opt run` with `budget=` the points done + N, `--dry-orchestration` → `--plan`, `--cadence-cshrc F` → `--cshrc F`.
